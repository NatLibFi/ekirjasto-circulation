# Text search options

The existing `/search` and `/search/<lane_identifier>` routes accept two optional
parameters for text searches. Existing clients can omit both parameters: the
default query, response format, analyzers, and index schema are unchanged.

| Parameter | Default | Accepted values |
| --- | --- | --- |
| `search_field` | `all` | `all`, `title`, `author`, `classification`, `genre`, `summary` |
| `include_summary` | `true` | `true`, `false` |

Examples (append to the library's search URL):

```text
?q=romantiikka&include_summary=false
?q=romantiikka&search_field=title
?q=romantiikka&search_field=genre
?q=dog&search_field=summary&language=eng
```

`search_field=all` uses the existing multi-field search. Setting
`include_summary=false` removes the description (`summary`) from the topic
matching hypothesis in that search and from recursive queries generated by the
query parser. It does not exclude books that also contain the search term in
their description. Genre, audience, fiction-status, and target-age terms
recognized by the existing query parser can still act as filters in `all` mode.

A specific `search_field` searches only that field and takes precedence over
`include_summary`. Thus `search_field=summary&include_summary=false` still
searches the description. Field-only searches do not interpret genre, audience,
fiction-status, or target-age words as additional filters. Title search
excludes subtitles. Author search includes the primary author and contributors
with primary-author or author roles, excluding narrator-only contributions.

Classification searches use the analyzed `classifications.term` field. Genre
searches use the nested analyzed `genres.name` field, so a query can match parts
of a genre name; it is not an exact whole-name lookup. Available names and
classification terms depend on indexed metadata; these parameters do not
translate them or provide a list of selectable values.

Existing language, availability, collection, distributor, and ordering options
can be combined with these parameters. Field-only searches do not apply the
default score cutoff used when sorting multi-field search results by metadata;
that cutoff is not calibrated for single-field scores. An explicitly supplied
internal minimum score is still respected.

The active options are retained in search feed URLs and facet navigation.
Unsupported fields, malformed boolean values, or non-default text search options
combined with `search_type=json` produce an invalid-input response (HTTP 400).
Existing JSON searches remain unchanged.

## Genre and classification checkboxes

Call `GET /search_filter_values` on the library's API base URL to get the
available values. The route supports the same library path or subdomain forms
as other library endpoints; for example:

```text
https://catalog.example.org/MAIN/search_filter_values
```

It returns genre and classification options for books that are searchable in
the library's collections. A book is counted when its
work is presentation-ready and its collection license pool is not suppressed;
it must have an open-access license or an owned license. When the library does
not allow holds, results are further limited to open-access, unlimited-access,
or currently available license pools. Each option includes a count of distinct
works. Classification options include only the BISAC scheme currently indexed
for search. The result is cached for one hour per collection set and
`allow_holds` setting. Options without a usable genre name or classification
term are omitted.

The response is JSON with this shape (values below are illustrative):

```json
{
  "genres": [
    {"id": 12, "name": "Romance", "count": 245}
  ],
  "classifications": [
    {
      "scheme": "http://www.bisg.org/standards/bisac_subject/",
      "identifier": "FIC027020",
      "term": "Romance",
      "name": "Romance",
      "count": 180
    }
  ]
}
```

Use `genres[].id` for `genre` parameters and `classifications[].term` for
`classification` parameters. The label can be shown from `name`, and `count`
is the number of distinct works matching the option in the endpoint's scope.
The endpoint returns empty arrays when the library has no collections or no
matching values.

The app should fetch this endpoint from the same library API base URL it uses
for search, then build its genre choices from the returned `genres` array. For
each item, show `name` (and optionally `count`) as the choice and retain that
item's `id` as the value to send in `genre`. Do not hard-code IDs: they come
from the endpoint response and may differ between environments or libraries.
For example, the illustrative response above would produce a choice labeled
`Romance` with value `12`.

These three parameters have separate roles:

- `q` is the search text, for example `romantiikka`.
- `search_field=genre` tells the search to look for the `q` text in book genre
  metadata.
- `genre=<id>` is a filter that restricts results to a selected genre. Get the
  ID from that genre's `id` in the `/search_filter_values` response.

For example, `?q=romantiikka&search_field=genre` searches for "romantiikka" in
genre metadata. `?q=romantiikka&genre=12` searches for "romantiikka" using the
default search fields, then restricts the results to genre ID `12`. The ID is
illustrative; use the actual ID returned for the chosen genre. To do both,
combine the parameters: `?q=romantiikka&search_field=genre&genre=12` searches
genre metadata for the text and filters results to the selected genre.

Send selected options as repeated parameters alongside the search:

```text
?q=romantiikka&genre=12&genre=27&classification=Romance&classification=Romantic Fiction
```

URL-encode parameter values when building the request (for example, encode
spaces and non-ASCII characters). Keep each selected value as a separate query
parameter; do not join multiple values with commas. To clear a filter, omit all
instances of its parameter. To clear all checkbox filters, omit both `genre`
and `classification` while retaining any other search parameters. Search
navigation links produced by the server preserve active search fields and
checkbox selections.

Selected genre IDs are ORed with each other, as are selected classification
terms. Selecting at least one genre and at least one classification requires a
book to match a selected genre and a selected classification (AND between the
groups). These filters apply with either `search_field=all` or a field-scoped
text search. Genre values use IDs; classification values use the indexed term.
The endpoint returns classification terms with `/` replaced by spaces to match
the term stored in the search index. Currently, only BISAC classification
values are returned. The endpoint response is cached for up to one hour, so
newly imported metadata or availability changes may take up to an hour to be
reflected in the option list and counts.

## Example user flows

### Search by a word, then limit the search to book titles

Suppose a user searches for `the joy of AI` and then chooses **Title** from the
app's **Search in** dropdown. Send the same query with `search_field=title`:

```text
?q=the%20joy%20of%20AI&search_field=title
```

Changing the dropdown back to **All fields** should omit `search_field` (or set
it to `all`). The app can keep the query text unchanged while changing this
parameter.

### Search for nonfiction, then filter by classification and genre

Suppose a user searches for `tietokirja` and selects a classification and a
genre from filter controls. First call `/search_filter_values` and populate the
controls from `classifications` and `genres`. Send the selected
`classifications[].term` as `classification` and the selected `genres[].id` as
`genre`, alongside the query. For example, if the selected response values
were `Nonfiction` and genre ID `12`:

```text
?q=tietokirja&classification=Nonfiction&genre=12
```

`Nonfiction` and `12` here are illustrative values; use the values returned by
the endpoint for the target library. With both parameters present, matching
books must match the text query, the selected classification, and the selected
genre. To remove either selection, omit its parameter and retain the others.

No reindexing is required. Applications must add their own controls and send the
new parameters to expose these options to users. For example, show a "Search in"
selector and offer an "Include descriptions" toggle when "All fields" is selected.
